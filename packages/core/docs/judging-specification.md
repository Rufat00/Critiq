# Critiq: Mathematical Specification for Fair Judging and Room-Aware Orchestration

**Status:** Technical design proposal (not implemented)  
**Version:** 1.0 — 17 November 2026  
**Scope:** mutually exclusive tracks; overlapping cross-track challenges; relative, rubric, and ordinal endorsement judging; room-aware automated judge dispatch; readiness and reliability; `@critiq/core` implementation design.

> **Design principle.** No scoring formula can rescue a disconnected, systematically biased assignment plan. Critiq must jointly design who judges whom, the evidence collected, how scores are aggregated, and how uncertainty is communicated. This document distinguishes _normative product choices_ from _statistical guarantees_. Parameters below are proposed defaults, not scientifically established universal constants.

## Executive decisions

1. A project belongs to **exactly one track**, and **Overall is a track**, not an additional award automatically shared by all entries. Multiple challenge entries are allowed regardless of track.
2. Each track/challenge is a separate competition with its own eligibility, method, qualified judges, coverage policy, results, and audit trail. A physical visit can create multiple category evaluations but must not falsely count as multiple independent judges.
3. `RELATIVE` collects a complete personal ordering for each judge within a track. Use pairwise-majority Copeland as the **simple, auditable default**; do not assign artificial ties to unobserved pairs. Require comparison-graph connectivity for an unqualified global ranking. A regularized Bradley–Terry model is a diagnostic / separately versioned alternative, not a silent replacement.
4. `RUBRIC` aggregates validated weighted criteria into a 0–100 evaluation score and then a project mean. Expose judge calibration diagnostics. **Do not** automatically z-normalize based on small, unbalanced judge portfolios.
5. `RATING_SCALE` is a five-level ordinal recommendation to win: **Definitely no; Probably no; Unsure; Probably yes; Definitely yes**. The official V1 leaderboard uses a published ordinal, pairwise win-probability procedure (defined below), with vote distributions always visible. Avoid pretending that Likert categories are equidistant physical measurements.
6. Coverage minimum and maximum are configured for each competition or inherited from event defaults; the system derives a **feasible target**, estimated workload and shortfalls from available judge-minutes, room conditions, and qualifications. Suggested initial event defaults: min 3, max 9, desired 6 (only if feasible).
7. The room parameter `minRoomCompletionPercent` (default **25**, valid **0–100**) is a _minimum stay condition_: a judge becomes **eligible** to move after completing that fraction of room projects, rather than being forced to move. A 100% rule can deadlock under project unavailability; explicit emergency/organizer overrides and infeasibility reporting are necessary.
8. Hard constraints precede optimization. During normal dispatch optimize, in order: prevent uncovered projects, complete minimum coverage, keep comparison/calibration graphs connected, balance independent judges, reach targets, resolve close finalists, then minimize travel. Never let scoring uncertainty push projects below minimum coverage.
9. Results are _provisional_ until coverage and structural requirements are met. Disconnected or under-covered categories require explicit organizer acknowledgment before final publication, with reason audited.
10. All math belongs in pure functions in `packages/core/src/judging/`; business queries, writes, authorization, transactions, and audit remain within core. Web server actions are thin transport adapters; `packages/db` contains persistence only.

## 1. Formal model and invariant definitions

Let `P` be submissions, `J` judges, `R` rooms, `T` tracks, and `C` challenges. Define the competition set `K = T ∪ C`. The set of projects eligible for competition `k` is `P_k`, and the authorized judges are `J_k`. Every project `p` has exactly one track `t(p) ∈ T`, including the possible track named Overall:

`sum_{t ∈ T} x[p,t] = 1`, where `x[p,t] ∈ {0,1}`.

Challenges are independent, with `y[p,c] ∈ {0,1}`, and `sum_c y[p,c]` unrestricted within organizer-defined entry limits. Competition eligibility is defined by `x` or `y`, not by inferred association of track scores. In particular, being ranked first in Beginner cannot automatically translate to Best AI.

An evaluation unit is **(judge, project, competition)**. A physical **visit** is **(judge, project, assignment)** and may contain several explicit evaluation units. For relative competitions a completed judge–project observation participates in a versioned ordered list; pairwise judgments are _derived_ from the list. They are not independent evidence points when generated by the same judge.

Distinct judge coverage for project `p` in competition `k` is:

`n[p,k] = |{ j : a completed, valid evaluation exists for (j,p,k) }|`.

Each distinct `j` counts at most once, even across resubmissions. `pending[p,k]` counts feasible, active, reserved evaluations targeting that competition. `effective[p,k] = n[p,k] + pending[p,k]` is used **for dispatch capacity**, not for published coverage. Expired/canceled reservations are not counted.

**Constraints/invariants:**

- One track per eligible project; Overall is mutually exclusive with all specialized tracks.
- A judge cannot evaluate an excluded/unauthorized competition, conflicted project, invalid submission or canceled visit.
- At most one valid final evaluation per `(judge, project, competition)` unless a deliberate revision protocol replaces the previous version.
- Track and challenge judging data never leak into each other's official scores.
- An opt-in challenge is evaluated only if project is eligible, the judge is qualified for that challenge, and the visit explicitly targets it.
- Every official scoring version specifies its algorithm, hyperparameters, rubric/labels, rounding, and tie policy before judging begins.

### Example

Alpha belongs to Beginner, enters Best AI and Best UX. Beta belongs to Overall, enters Best AI. Gamma belongs to Advanced, enters Best UX. Alpha has one track evaluation and potentially two challenge evaluations, independently calculated. There is **no** Alpha-versus-Beta track comparison; a Best AI competition may compare Alpha and Beta legitimately.

## 2. Common mathematical foundations

### 2.1 Coverage and fairness

Let `m_k` be the minimum distinct judges per eligible project for competition `k`, and `M_k` the maximum. A target `q_k` must satisfy `m_k ≤ q_k ≤ M_k` if feasible. Configuration validity does not imply schedule feasibility.

Coverage deficits are:

`minimumDeficit[p,k] = max(0, m_k − effective[p,k])`  
`targetDeficit[p,k] = max(0, q_k − effective[p,k])`  
`completedMinimumDeficit[p,k] = max(0, m_k − n[p,k])`.

An aggregate average hides disparities: use _minimum_ per-project coverage as a primary readiness gate. Also report coverage rate, lower-decile coverage and variance:

`coverageVariance[k] = (1/|P_k|) Σ_p (n[p,k] − meanCoverage[k])²`.

Variance is only a secondary fairness diagnostic; a project with no qualified judges is a feasibility problem, not an excuse to lower its target silently.

### 2.2 Separate observation, score and confidence

An observation is what a judge submitted. An aggregation is a deterministic function of observations and a frozen scoring configuration. Confidence/readiness is a separate function of coverage, disagreement, overlap and model assumptions. `score = 84` never means 84% probability that the project should win. Confidence intervals and win probabilities estimated by bootstrap or a model are conditional on assumptions and should be labeled accordingly.

### 2.3 No blind correction for judge bias

Judge severity, project strength and assignment are confounded when judges see different portfolios. Naive per-judge z-scores can penalize a judge who was deliberately assigned high-quality projects. A calibrated model requires connected judge–project overlap and enough judge observations. Prefer fair assignment design; present calibration as diagnostics until simulation demonstrates gains.

### 2.4 Tie and rounding policy

Keep full-precision numeric values in calculations. Round only in display (e.g., two decimals). An exact mathematical tie or a practically unresolved result must be shown for deliberation; **never** break official award ties via project ID, submission time or pseudo-randomness. Stable IDs may be used only for consistent non-award display ordering.

## 3. RELATIVE: track judging

### 3.1 Observation and elicitation

A judge evaluates a subset `H[j,k] ⊆ P_k` and maintains a full strict ordering `π[j,k]` of the projects they have judged for track `k`. The UI should let the judge insert or reorder the latest project. To avoid systematic primacy bias, judge UI should periodically show the complete ordering for review. If ties are allowed, a _separate_ explicit tie-aware model and UX are required; V1 should use a strict order plus an optional flag that two projects are very close.

One rank ordering of `h` projects yields `h(h−1)/2` pair observations, but they are correlated because one judge supplied all of them. A judge who sees more projects may contribute more pairs; that can overweight prolific judges. Critiq should track judge portfolio sizes and ideally balance them; optional judge-cluster weighting is a separately configured policy, not a default hidden adjustment.

### 3.2 Pairwise vote matrix

For ordered pair `(p,q)` define:

`W[p,q] = number of judges with both p and q in their track ranking who placed p above q`.

`N[p,q] = W[p,q] + W[q,p]`.

If `N[p,q] = 0`, the pair is **unobserved**. If `N[p,q] > 0`, `observedPreference[p,q] = W[p,q]/N[p,q]`. It is an empirical fraction, not a calibrated probability.

### 3.3 Official simple aggregator: observed-pair Copeland

Define for each observed unordered pair:

`h[p,q] = 1 if W[p,q] > W[q,p]; 1/2 if equal; 0 if less`.

`C[p] = Σ_{q != p, N[p,q]>0} h[p,q]`.

**Key limitation:** raw `C[p]` is **not directly comparable** when projects have different observed opponent sets. A project with more distinct opponents has more opportunities to score. Thus do not publish raw Copeland as a fair full ranking in an arbitrary sparse comparison graph. Use one of these policy modes:

- **Preferred V1:** require a comparison design with nearly balanced pair exposure and connected graph; calculate `C[p]` but mark low/unequal opponent coverage. If opponent exposure is markedly unequal, retain leaderboard as _provisional_ and direct additional judges to close gaps.
- **Fallback diagnostic:** `C_normalized[p] = C[p] / observedOpponentCount[p]`, for positive denominators. This corrects the count scale but **does not remove strength-of-schedule bias**, so it is not a mathematical cure.
- **Model-based:** regularized Bradley–Terry ranking (below) can estimate strengths from unbalanced but connected graphs, with model assumptions and diagnostics.

A robust production policy is to predeclare which estimator is official for a competition; a particular event may choose **regularized Bradley–Terry** as official for sparse schedules, while keeping Copeland as an explanatory diagnostic. Do not change after judges see projects.

### 3.4 Bradley–Terry strength model

For project strengths `θ_p`:

`Pr(p beats q) = sigmoid(θ_p − θ_q) = 1/[1+exp(−(θ_p−θ_q))]`.

Fit `θ` by maximizing weighted pairwise log-likelihood with an L2 penalty:

`L(θ) = Σ_{p<q} [ W[p,q] log σ(θ_p−θ_q) + W[q,p] log σ(θ_q−θ_p) ] − (λ/2)Σ_p θ_p²`.

Enforce `Σ_p θ_p = 0` (or fix one reference) for interpretability. Regularization prevents estimates from diverging for undefeated projects; it does **not** create data linking disconnected comparison components. Strong connectivity of the _directed win graph_ is the classical requirement for a finite, unique unregularized Bradley–Terry maximum-likelihood fit (after identifiability constraints). Mere undirected connectivity is necessary for cross-project information but is not sufficient for the unregularized MLE. Use connected-component diagnostics even with regularization.

Pairwise results induced by the same full judge ranking are not independent, so standard errors from an independent-pairs likelihood are overconfident. Estimate uncertainty by re-sampling **judges as clusters**, refitting the model; emphasize that each estimate is conditional on observed judges and assignment design.

**Recommended policy:** use regularized BT as the official sparse-graph default **only after** benchmarking it against balanced Copeland across realistic simulations. Until that testing, keep official aggregation configurable and clearly declared; the algorithm implementation must support both versions.

### 3.5 Reliability diagnostics

Build `G_k = (P_k, E_k)` with edges where `N[p,q]>0`. Report:

- connected components (including isolated submissions), degree distribution, minimum degree and fraction of observed pairs;
- pair-exposure distribution and judge portfolio distribution;
- bootstrap top-1 and top-3 selection frequency, resampling judges;
- contradictory cycles, large Copeland-vs-BT rank differences, and whether winner depends on underexposed comparisons.

Connectedness alone is **not** sufficient for statistical precision. A graph linked by one very thin bridge is fragile; measure edge redundancy and optionally algebraic connectivity (`λ₂` of the undirected Laplacian) as a _diagnostic_, not a required V1 dependency.

### 3.6 Example of failure of unbalanced Copeland

A defeats B and C, B defeats C, while D is only compared once and defeats C. Raw wins: A=2, D=1. The data do **not** establish how D compares with A or B, and D should not be treated as necessarily inferior because it had fewer opportunities. Dispatch judges who already saw A or B to D, respecting room-stay rules, so those comparisons become observed.

## 4. RUBRIC: tracks and challenges

### 4.1 Frozen weighted criteria

For competition `k`, define criteria `i=1..d`, positive weights `w_i`, allowed minimum `l_i`, maximum `u_i`, and observed judge value `s[p,j,k,i]`. Normalize _each criterion separately_ before weighting:

`z[p,j,k,i] = (s[p,j,k,i] − l_i)/(u_i−l_i)`; requires `u_i > l_i`.

`X[p,j,k] = 100 * [Σ_i w_i z[p,j,k,i]]/[Σ_i w_i]`.

This avoids implicitly favoring criteria with larger numerical ranges. Example: innovation 40%, implementation 35%, presentation 25%, scores 8/10, 9/10, 7/10 on a **0–10 scale** yield `X=81`. If the configured scale is **1–10**, normalized values differ; do not assume scales start at zero.

If a criterion is mandatory, require a valid response. If `not applicable` is permitted, its effect on denominator must be configured before judging (e.g., exclude and renormalize, or require organizer approval); do not silently redistribute weights. Store criterion-level raw scores and rubric version alongside each submitted evaluation.

### 4.2 Project-level aggregation

For `n[p,k]` distinct completed, valid judges:

`rawMean[p,k] = (1/n) Σ_j X[p,j,k]`.

Also report median, sample SD (only when `n>=2`) and count. Weighted averaging across judges should normally be avoided unless expertise weights were predeclared and balanced across projects; objective eligibility for judging a challenge is preferable to ad hoc per-judge score weights.

**Why not total scores?** Totals award extra points simply for receiving extra judges.

### 4.3 Calibration diagnostics and optional model

A judge/project additive model is:

`X[p,j,k] = μ_k + α_p + b_j + ε[p,j,k]`, with `Σ_p α_p=0` and `Σ_j b_j=0` (or appropriate reference constraints).

Estimate `α_p` and `b_j` with regularization; with few reviews or isolated panels the parameters are weakly identifiable. Raw judge means are not sufficient to infer bias if project quality differs by judge portfolio. V1 should compute judge severity spread, pairwise shared-project overlap, and raw versus candidate calibrated ranking **for diagnostics only**. Releasing calibrated results officially should require explicit algorithm selection before judging, adequate overlap, measured improvement in simulation, and a plain-English explanation of adjustment.

### 4.4 Uncertainty

`SE = s/√n` describes variability under strong simplifying assumptions; with `n=3` or `4` it is unstable. Identical few scores yield `s=0` but not zero epistemic uncertainty. Prefer judge-cluster bootstrap or a hierarchical model when there is sufficient connected data; show _insufficient evidence_ rather than a falsely precise interval for very small counts.

### 4.5 Track versus challenge rubrics

Each competition owns its **own rubric and official score**. Do not reuse a track rubric to evaluate a challenge merely because it asks related questions. If a visit evaluates a track and a challenge, collect their distinct criteria separately; either one can be incomplete without falsely marking the other complete.

## 5. RATING_SCALE: ordinal recommendation to win a challenge

### 5.1 Five-level vote design

Prompt: **“Should this project win [Challenge Name]?”**

Proposed frozen options (organizers may customize wording before judging, but **not the order**):

1. `DEFINITELY_NO` — Definitely should not win
2. `PROBABLY_NO` — Probably should not win
3. `UNSURE` — Unsure / needs comparison
4. `PROBABLY_YES` — Probably should win
5. `DEFINITELY_YES` — Definitely should win

These are **ordered categorical judgments**. Differences between categories are not necessarily equal; a 5 is not “five times” a 1. The middle option should mean a neutral/uncertain assessment, not a missing vote. Missing responses are excluded from numerator and denominator and remain visibly missing.

A judge must judge all challenge entries against the same published challenge objective, not against their track. Sponsors may supply a concise award definition and eligibility rules. If the real intention is _comparative selection among finalists_, a final ordinal vote alone cannot guarantee choosing one winner; deliberation or dedicated finalist head-to-head voting can supplement it.

### 5.2 Official V1 candidate: ordinal superiority score

For project `p` with observed vote category frequencies `f_p(r)`, define the empirical distribution `F_p(r)=f_p(r)/n_p` for `r=1..5` (only when `n_p>0`). Define its pairwise superiority against project `q` as:

`O[p,q] = Σ_{r=1}^5 Σ_{s=1}^5 F_p(r) F_q(s) * [1(r>s) + 0.5 * 1(r=s)]`.

`O[p,q]` is the estimated chance that a randomly sampled rating for `p` exceeds a randomly sampled rating for `q`, with ties split evenly. It honors **ordinal order without assuming numerical category spacing**. For every observed pair with positive counts, `O[p,q]+O[q,p]=1`.

An overall superiority score within challenge `k` is:

`A[p] = (1/(|P_k|−1)) Σ_{q∈P_k,q≠p} O[p,q]`, if all competitors have valid votes and `|P_k|>1`.

This is an intuitive rank index: the expected fractional win versus a uniformly sampled rival (using the observed vote distributions). It is **not** a probability that `p` is truly the best project. A final award needs minimum coverage and uncertainty checks. Project samples with different judges can be confounded by judge severity; use balanced panels / overlap.

**Small-sample regularization (optional and predeclared):** before calculating `F`, apply a symmetric Dirichlet prior to the five category counts:

`F*_p(r) = [f_p(r)+α_r]/[n_p+Σ_s α_s]`.

For example `α_r=0.5` each is a _hypothetical tuning choice_, not a proven default. This reduces extreme rankings from 1–2 votes but shrinks results toward the prior, so include it only if simulation demonstrates value, and freeze the prior before judging. The preferred V1 launch can simply require minimum coverage and use unsmoothed frequency distributions.

### 5.3 Worked example

Alpha gets `DEFINITELY_YES, PROBABLY_YES, PROBABLY_YES`. Beta gets `DEFINITELY_YES, DEFINITELY_YES, DEFINITELY_NO`. Alpha has lower _peak_ enthusiasm but more consistent support. `O[Alpha,Beta]` sums all nine cross-vote pairings (with 0.5 for ties), rather than imposing arbitrary numerical distances. Calculate and present full vote histograms and pairwise result before ranking; a sponsor can see why the outcome occurred.

### 5.4 Alternative: ordinal cumulative-link model (later)

For category threshold `r ∈ {1,2,3,4}`:

`logit Pr(Y[p,j] ≤ r) = τ_r − θ_p − b_j`, with `τ_1<τ_2<τ_3<τ_4`.

Here `θ_p` is latent project endorsement and `b_j` represents judge severity. Fit with appropriate regularization and sufficiently connected assignments. This model respects the ordinal scale and can estimate judge effects, but is substantially harder to validate, explain, and run robustly on tiny events. Do not ship it as an automatic black-box correction in V1.

### 5.5 What if every judge chooses “Probably yes”?

Everyone ties. The system must not fabricate distinctions; request a structured finalist comparison or organizer deliberation. If each project has only one or two ratings, mark the leaderboard as provisional even if ordinal superiority yields a formal score.

## 6. Feasibility planner before judging starts

### 6.1 Organizer-facing controls

**Required inputs:** per-competition (or inherited) `minimumEvaluations`, `maximumEvaluations`; judges and qualified competition assignments; available judging window; project-room assignment; estimated minutes per visit; room threshold `0..100` (default 25). Optional `desiredEvaluations`; unavailable projects and planned breaks. Do not require organizers to understand operations research: show a recommended target, workload estimate and clear warnings.

**Basic feasibility checks:** for competition `k`, there are `N_k=|P_k|` eligible projects, `J_k` qualified judges. Each judge can evaluate a given project only once:

`m_k ≤ M_k`, `m_k ≤ |J_k|`, and `M_k ≤ |J_k|` if the maximum is intended as attainable, not merely a cap. If `m_k > |J_k|`, minimum is impossible.

`D_min,k = N_k * m_k`, `D_target,k = N_k * q_k`, and `D_max,k = N_k * M_k` count **category evaluations**, not necessarily physical visits. If one judge visits one project and fills two qualified category forms, that is two category evaluations but one visit. Conversely, two simultaneous judges each consume a separate visit and capacity.

### 6.2 Time capacity and physical visits

For judge `j`, `B_j` is available active judging minutes after breaks. If estimated evaluation time is `d_jp` minutes and room movement time `t_rr'` minutes, then:

`Σ_{visits v assigned to j} d_v + Σ_{consecutive room transitions} t_rr' ≤ B_j`.

Multi-category visit time is **not always additive**: presentation is shared but each additional form has marginal completion time. A useful parameterized estimate is:

`d_visit(p,j,S) = d_presentation(p) + d_questions(p,j) + Σ_{k∈S} d_form(k)`.

Organizers should see **conservative, expected, optimistic** total visit capacity scenarios. A simple upper bound is `Σ_j floor(B_j / min_d_j)`, but it ignores competing qualifications, travel and room stays and must not be called a feasible plan.

### 6.3 Qualification-aware lower bounds

For every competition `k`, at least `m_k` distinct judges must be eligible for each project. More strongly, consider subset `U ⊆ P_k`: judges qualified for projects in `U` must jointly possess enough available slot capacity to provide `m_k |U|` distinct reviews with per-pair capacity 1. This is a capacitated bipartite matching/flow condition; checking only `|J_k|` is insufficient.

A _coverage max-flow relaxation_ provides a defensible feasibility test:

`source → judges (capacity estimated visit/competition slots)`  
`judges → project-category nodes (capacity 1 if eligible)`  
`project-category nodes → sink (demand m_k, optionally q_k)`.

For multiple competitions and shared visits, this relaxation can overestimate needed physical visits or be loose in the opposite direction if category-specific times are ignored. The **accurate** full planning problem is a time-indexed assignment/scheduling optimization with one visit able to fulfill multiple category demands. V1 can implement a greedy joint-visit planner with conservative timing and a repair pass, label it **estimated feasible**, then run simulation or an optimizer later. Avoid declaring mathematically proven feasibility from a heuristic.

### 6.4 Selecting the recommended target

Do **not** define `q = floor((m+M)/2)` automatically. It ignores people and time. Instead:

1. Test feasibility of meeting every minimum, with judge/project qualifications and estimated time.
2. If infeasible, show the minimum shortfall by competition/project and concrete remedies (more judges, longer window, narrower eligibility, or lower minimum). Do not silently reduce minimum.
3. If feasible, increment a shared target vector gradually from `m` toward a desired goal or `M`, distributing extra projected visits to competitions with greatest marginal fairness benefit and allowing shared multi-category visits.
4. Stop when the next increment exceeds conservative remaining capacity or risks a broken room schedule.
5. Return recommended integer `q_k`, per-project planned quotas, slack time, judge load, and risk level.

A binary search on uniform target `q_k` can accelerate one-competition feasibility checks because feasibility should be monotone in the requested quota. For multiple overlapping competitions, coordinate target increments jointly; separate per-category maxima cannot simply be added as independent physical visits.

### 6.5 Worked planning illustration

Suppose **120 projects**, **24 judges**, an estimated **12 physical visits per judge** in the available window, and one track category per project. Estimated total capacity = `24×12=288` visits. For `min=3`, the minimum requires `120×3=360` track visits: **infeasible** even before room travel. Setting `max=9` does not make a target of 6 or 7 possible. With the same capacity, the optimistic upper bound for uniform coverage is `floor(288/120)=2`, below the configured minimum. The organizer must add judges/time or lower the minimum. An overlapping challenge may sometimes be scored during a track visit, but doing so does **not** reduce the 360 distinct track-judge requirements.

Now suppose the window permits **25 visits per judge**: capacity = 600 track visits before travel, uniform upper bound 5. A feasible `q=5` still depends on judge room allocation, qualifications, and room movement rules. A robust planner may recommend 4 to preserve slack for delays.

### 6.6 Buffer and real-time recalculation

Reserve estimated time slack, e.g. a configurable **10–20% planning reserve** as an initial simulation assumption, not a universal rule. Recompute expected completion continuously from actual median presentation lengths, available judges, projects paused and judging time remaining. The committed minimum remains a requirement; if it becomes infeasible, show a clear escalation and audited organizer override.

## 7. Room-stay threshold: mathematical definition

### 7.1 Exact meaning of 0–100%

Let room `r` contain `N_r` eligible projects in the current judging session's **frozen room roster snapshot**. When judge `j` enters room `r`, record `visited[j,r,epoch]`, the distinct projects for which `j` completed a valid visit **while in that room during that epoch**. A visit is counted once regardless of how many competitions it covers.

`roomCompletion[j,r,epoch] = 100 * |visited[j,r,epoch]| / N_r`.

`minStayVisits[r] = ceil((roomThresholdPercent/100) * N_r)`.

`canMoveNormally = (distinctCompletedRoomVisits >= minStayVisits)`.

When `N_r=0`, room is unavailable; dispatch should never create a stay epoch there. At threshold 0, movement is immediately eligible. At 25% for a 12-project room, require `ceil(0.25×12)=3` completed projects. For a 7-project room require `ceil(1.75)=2`. At 100% require all 12 or all 7 — **unless an exception is needed**.

**Recommended semantic choice:** each entry into a room starts a _new stay epoch_, so the percentage is based on project visits completed during that stay. Do not silently carry progress from a previous entry into the room. The frozen denominator prevents dynamic submissions/room reassignments from moving the goalposts halfway through a stay.

### 7.2 Important alternative: unique-room coverage instead of visit-epoch coverage

If the intended UX is **“the judge should have seen 25% of all room projects in total”**, use unique lifetime completed visits in the room, not per-entry epoch. This is easier for judges to satisfy across repeat visits but is weaker at preventing room hopping late in the event. **Recommendation: per-entry epoch** with clear UI copy: “Visit 3 projects in this room before moving.” Both semantics must not be conflated; store a named policy version.

### 7.3 Threshold is permission, not command

After the requirement is met, the judge **may** move. They should continue in the current room if suitable assignments remain and moving would add unnecessary travel with negligible fairness benefit. A simple hysteresis rule:

`move only if utility(nextBestOtherRoom) − utility(nextBestCurrentRoom) > movementPenalty + hysteresisMargin`.

A minimum improvement margin prevents oscillation. For a judge with no feasible local project, test whether movement is allowed, then offer an external-room assignment. A room change should be an intentional dispatch decision with persisted origin/destination and planned walk time.

### 7.4 Deadlock avoidance and 100% threshold

The threshold **must not** make the scheduler violate other hard constraints. Example: 12 projects are in Room A, judge has evaluated 10, two remaining are conflicted/absent, threshold is 100%. No legitimate local project exists: a strict no-exception policy strands that judge forever.

Define override reasons: `NO_FEASIBLE_LOCAL_PROJECT`, `PROJECT_UNAVAILABLE`, `URGENT_MINIMUM_COVERAGE`, `ROOM_CLOSED`, `JUDGE_BREAK`, `ADMIN_OVERRIDE`, `EVENT_ENDING`. An override allows a safe move **but is audited and counted in room-threshold diagnostics**. Do not auto-assign conflicted projects to satisfy the threshold.

An organizer may choose **hard** versus **soft** threshold policy; recommended default is **soft with named safety/feasibility overrides**. For 100%, display an explicit warning that it may slow cross-room comparison connectivity and make some minimums infeasible.

### 7.5 Room-specific and competition-specific pitfalls

A judge assigned solely to Best AI may be qualified for only two projects in a room of twelve. If the threshold is 25% of all room projects (three visits), the stay is impossible. To avoid misleading math, calculate a **reachable room denominator** as the number of distinct projects for which the judge has at least one valid eligible category at room-entry time. For example, if only two projects are judge-eligible, at 25% require `ceil(0.25×2)=1`, not three.

However, the product phrase “25% of projects in their room” might imply the physical roster denominator, not eligible projects. Thus specify **two denominators**: `physicalRoomSize` for display and `judgeReachableRoomSize` for enforceable requirement; enforce against judge-reachable room projects, freeze at entry, and always show “1 of 2 eligible projects visited (room has 12 total).” Alternatively allow organizers to enforce the physical denominator with a feasibility warning and automatic fallback. Never hide the choice.

### 7.6 Room scheduling and comparison graph

Room concentration cuts travel but can fragment relative comparison graphs if judges never compare projects across rooms in the same track. Assign deliberate **bridge judges** to multiple rooms _after satisfying their stay_. Preplan a small set of bridge transitions and prioritize connecting components over redundant local review when minimum coverage is safe. Avoid bridge selection that repeatedly uses only one judge: that creates a fragile link and over-concentrates influence.

## 8. Assignment orchestrator and objective

### 8.1 Candidate actions

At a judge's next-visit request, candidate actions are `(judge j, project p, targeted competition set S)` where `S ⊆ eligibleCompetitions(j,p)` and `S≠∅`. `S` may include the project's sole track and any eligible challenges. Target categories whose maximum `M_k` is reached by `effective[p,k]` are excluded, absent explicit authorized reopening. Do not force a judge to complete every optional category merely because it is present.

Candidate actions must satisfy authorization, judge status, no self/conflict of interest, project state and readiness, physical capacity, no duplicate active reservation/evaluation, enough remaining estimated time, and room threshold if moving. A preview may be stale; **revalidate inside the reservation transaction**.

### 8.2 Hierarchical objective (lexicographic)

Instead of trusting one magic weighted utility score, compare candidate plans by priority tiers:

**Tier 0: hard feasibility.** Reject any invalid action.  
**Tier 1: prevent stranded minimums.** Prefer projects with urgent minimum deficits and scarce qualified judge options.  
**Tier 2: restore structural connectivity.** Within comparable Tier-1 options, maximize connections among relative projects and cross-panel rubric overlaps.  
**Tier 3: balance judge diversity and target coverage.** Reduce concentration, distribute evaluations across projects, and fill target deficits.  
**Tier 4: improve ambiguity at award boundary.** Once minimums are safe, gather targeted evidence for close finalists rather than repeatedly reviewing obvious leaders.  
**Tier 5: logistics.** Reduce walks, avoid room switching and balance queues.

Within each tier use calibrated, documented numerical scoring; compare tiers lexicographically to prevent a short walk from outranking a project at risk of zero evaluations. In emergency mode, Tier 1 may dominate all other soft priorities.

### 8.3 Scarcity and deadline urgency

Let `eligibleRemainingJudges[p,k]` count judges who could still validly evaluate `(p,k)` and have feasible remaining time, including future rooms. Define:

`scarcity[p,k] = mRemaining[p,k] / max(1, eligibleRemainingJudges[p,k])`.

For `mRemaining>eligibleRemainingJudges`, declare an imminent impossibility; raise an organizer alert rather than just increasing score. Add expected remaining presentation slots and temporal availability to distinguish projects leaving soon from those available all session.

The scheduler should optimize **minimum _future_ feasibility**, not just current deficits: a judge who is the _only_ person qualified for Best Hardware should generally not be spent solely on generic track reviews when equally qualified generic judges are available.

### 8.4 Relative comparison information gain

When judge `j` has already ranked `H[j,k]` projects in relative track `k`, adding `p` creates new pair opportunities with each `q∈H[j,k]`, only after the ranking is submitted:

`pairGain[j,p,k] = Σ_{q∈H[j,k]} 1/[1+N[p,q]]`.

Add a larger, bounded bonus for connecting separate graph components. This is a **heuristic**: the `1/(1+N)` form does not have a universal optimality proof. Distinguish diversity across _judges_ from number of pairs contributed by one prolific judge. Penalize excessive repeated co-judging by the same panel and target redundant bridges.

### 8.5 Rubric and ordinal information gain

For rubric and rating-scale categories, prioritization should emphasize missing minimums, qualified-judge scarcity, shared-project links across judge cohorts, score variance and finalist uncertainty. Do **not** automatically send every extra judge to whichever project currently ranks first; under a noisy ranking that creates rich-get-richer feedback. Use a minimum quota first and hold out some extra assignments for randomly selected well-balanced projects to prevent adaptive selection bias.

### 8.6 Diminishing returns with overlapping challenges

One visit may improve several competitions, but projects in many challenges must not monopolize judge time. Define marginal demand for each targeted competition and cap or discount benefit above target:

`gain(p,k) = 1 if n+pending<m; β if m≤n+pending<q; 0 if n+pending≥q`, where `0<β<1` is configurable only after testing.

A joint visit's benefit is the union of legitimate category deficits, minus marginal form time and category imbalance penalties. Fairness is evaluated **separately within each competition**. No rule requires every project to receive equal _total_ visits across dissimilar challenge counts; equal opportunity means adequate independent coverage within the awards they enter.

### 8.7 Batch versus greedy dispatch

Sequential greedy dispatch can reserve the last specialist for a generic project while making a niche challenge impossible. Preferred approach:

1. Precompute a near-term batch plan for currently available judges and projects (e.g., all idle judges).
2. Reserve category-specialist assignments to satisfy constrained minimums.
3. Optimize remaining matches by lexicographic objective and room logistics.
4. Atomically claim one next visit per requesting judge; replan when projects/judges become unavailable.

A bipartite max-weight matching can help for one-visit-per-judge dispatch windows, but room transitions, multi-category visits and future capacity make a full solution a richer scheduling problem. V1: greedy plus minimum-feasibility lookahead and swap/repair search; future: integer programming / min-cost flow with appropriately modeled constraints.

### 8.8 Deterministic scheduling + guarded randomness

Use deterministic scoring and stable snapshot IDs for audit and replay. Randomize only exact or near-exact scheduler ties with a recorded seed; deterministic favoritism by project ID can create long-run assignment bias. Never use randomness to decide award winners.

## 9. Formal planning model (extension-ready)

Introduce binary `x[j,p,s]` = judge `j` visits project `p` in slot `s`, and `z[j,p,k,s]` = that visit collects category `k`. Then:

`z[j,p,k,s] ≤ x[j,p,s]` and `z=0` if `(j,p,k)` ineligible.

`Σ_{j,s} z[j,p,k,s] ≥ m_k` and `≤ M_k` for every eligible `(p,k)`.

`Σ_s z[j,p,k,s] ≤ 1` for each `(j,p,k)`.

`Σ_p x[j,p,s] ≤ 1` per judge and slot, with additional project/station concurrency constraints.

Slot/time constraints must use **duration** and transition time; simple equal-length slots are approximations if visit times vary. Room threshold introduces per-judge, per-entry state and transition constraints: a room departure is allowed only after meeting the frozen reachable-room quota or recording an override. Multi-category visit durations are modeled by fixed presentation cost plus relevant form costs.

Practical optimizer objectives: minimize total unmet minimums first (with very large explicit penalties), then minimize disparity/weak connectivity, then minimize travel and assignment imbalance. The event must never announce a feasible solution from an optimization relaxation that omitted room stay or visit duration.

## 10. Lifecycle, readiness, tie handling, publication

Competition states recommended: `UNCONFIGURED`, `PLANNED`, `COLLECTING`, `MINIMUM_UNMET`, `READY_FOR_REVIEW`, `FINALIZED`, `FINALIZED_WITH_EXCEPTIONS`. These are **competition** states, not a replacement for the event's existing `DRAFT → READY → JUDGING → PAUSED → DELIBERATION → COMPLETED` stages.

A competition is `READY_FOR_REVIEW` when:

1. every currently eligible project has `n[p,k]≥m_k` (completed, not pending);
2. no active assignments remain whose results could overturn the frozen decision without explicit policy;
3. relative categories have adequate graph connectivity and exposure under the declared methodology;
4. the scoring version and eligibility snapshot are fixed, no score integrity violations remain;
5. uncertainties, ties and unfinished target quotas are disclosed to organizers.

Target achievement is a quality goal; minimum is an operational readiness gate, but organizers may override if unavoidable. A leaderboard can be computed before readiness but must say **provisional**. When first/second are close, show actual supporting evidence and permit deliberate finalist judging. If no judges remain, present unresolved tie and an audited organizer decision rather than secretly fabricating resolution.

For challenges with sponsorship restrictions or only 2 eligible judges, the minimum cannot be set to 3 without an explicit exception or additional judges. The system may recommend a lower category-specific minimum **before judging**, but must not silently weaken an active rule.

## 11. Security, consistency and concurrency

- All reads/writes are scoped to the **single hackathon installation**, authorized member and competition; do not introduce unrequested organization multitenancy.
- Core validates identity from trusted context and derives authorizations from DB; the browser must never supply its own judge ID, role, category membership or award authority as trusted facts.
- Unique constraints for one active evaluation per judge/project/competition; unique active assignment per judge; avoid duplicate project capacity claims with transaction locking and counters.
- Assignment reservations have `expiresAt`, heartbeat/renewal, cancel/skip reason, and idempotency token; expired reservations release `pending` counts.
- Revalidate availability, room threshold, qualification, project presence and max coverage inside an appropriately isolated transaction. If two requests race for the last slot, only one commits.
- Record event/config/scoring version, timestamp, source, judge and competition on all submissions. Store corrected versions or change history, not destructive overwrites.
- Exclusions (e.g., conflict discovered late) trigger deterministic recomputation of affected rankings, coverage and readiness, with a visible audit.
- Judge rankings are global per relative competition, not per individual project visit; use optimistic version checks to prevent overwriting a concurrently updated ranking.
- Business mutation and its audit insert commit in the same DB transaction. No network calls inside DB transaction; use outbox only when required.
- Close judging prevents unauthorized new scores; explicit organizer reopen is audited. Preserve previous published snapshots and indicate superseding revision.

### 12.2 Business workflow contracts

**`configureJudging(ctx,input)`** validates scope, track exclusivity, challenge membership, score settings, room policy, category-specific min/max and state; invokes feasibility planner; saves frozen configuration/version with audit. Before `READY`, updateable by organizers; after start, changes require an explicit audited amendment and recomputation.

**`requestNextAssignment(ctx,input)`** loads trusted judge identity/permissions and current room-stay epoch, rejects invalid states, gets a consistent snapshot, filters hard constraints, computes batch/greedy next candidate, atomically reserves visit/category targets, and returns short human-readable reason e.g. “Stay in Room B — project needs its 3rd judge.” Do not expose competitors' live confidential scores to judges.

**`submitRubricEvaluation` / `submitRatingVote`** validate assignment, competition and frozen policy; persist idempotently with audit, update category completion, recompute or invalidate results cache.

**`updateRelativeRanking`** validates a complete permutation of the judge's completed eligible relative-track projects; checks revision; updates ranking and derived pairs atomically or computes derived pairs lazily; recomputes impacted results.

**`completeJudgingVisit`** marks physical visit complete only after required targeted category evaluations are done or explicitly excluded/skipped with reason; updates room-epoch unique completed project count, releases reservation, and makes judge dispatchable.

**`moveJudge`** checks threshold, feasibility override and destination availability, records epoch and travel, and audits any exception.

**`finalizeCompetitionResults`** freezes output snapshot and evidence/config version, checks readiness, allows explicit privileged exception with reason, handles ties for deliberation, and publishes one official version.

## 13. Execution pseudocode

```ts
async function requestNextAssignment(ctx: AppContext, input: RequestInput) {
  const parsed = requestNextAssignmentSchema.parse(input);
  const judge = await requireAuthorizedJudge(ctx, parsed);
  return ctx.db.$transaction(async (tx) => {
    const state = await loadJudgingSnapshotForUpdate(tx, judge);
    if (state.activeAssignment) return state.activeAssignment; // idempotent
    const candidates = listFeasibleCandidates(state, judge);
    const ranked = scoreAssignmentCandidates(candidates, state);
    const chosen = selectNextAssignment(ranked, state);
    if (!chosen) return { status: 'NO_FEASIBLE_ASSIGNMENT' };
    await revalidateCandidateForUpdate(tx, chosen, state);
    const reservation = await reserveVisitAndCategorySlots(tx, chosen);
    await writeJudgingAudit(tx, ctx.actor, reservation);
    return reservation;
  });
}
```

The actual Prisma locking/transaction strategy depends on the existing schema and database constraints. Transactional replay must guard against state that changes after snapshot load; use unique indexes, conditional updates, advisory locks or serializable retries as appropriate, but do not assume an in-memory mutex works across processes.

```ts
function decideNextRoom(state: JudgeRoomState, candidates: CandidateVisit[]) {
  const local = bestCandidate(
    candidates.filter((c) => c.roomId === state.roomId),
  );
  const remote = bestCandidate(
    candidates.filter((c) => c.roomId !== state.roomId),
  );
  const required = Math.ceil(
    (state.frozenReachableProjects * state.minRoomCompletionPercent) / 100,
  );
  const thresholdMet = state.distinctCompletedInEpoch >= required;
  if (local && !thresholdMet) return { kind: 'STAY', candidate: local };
  if (!local && !thresholdMet && remote)
    return {
      kind: 'MOVE_EXCEPTION',
      candidate: remote,
      reason: 'NO_FEASIBLE_LOCAL_PROJECT',
    };
  if (!remote)
    return local ? { kind: 'STAY', candidate: local } : { kind: 'WAIT' };
  if (
    !local ||
    remote.utility > local.utility + state.movePenaltyAndHysteresis
  ) {
    return { kind: 'MOVE', candidate: remote };
  }
  return { kind: 'STAY', candidate: local };
}
```

**Caution:** pseudocode uses a single numerical `utility` in the room-switch example for readability. Actual candidate comparison should use lexicographic priorities; movement penalty applies only after hard feasibility and minimum-critical priorities have been resolved. If moving is necessary to avert infeasibility, an explicit override can bypass the ordinary stay threshold.

## 14. Test plan: pure mathematical properties and integration cases

### 14.1 Relative properties

- Each strict ranking of `h` unique projects yields exactly `h(h−1)/2` pair preferences.
- For a pair, `W[p,q]+W[q,p]` equals number of judges who ranked both.
- Reversing all judge preferences reverses pairwise majority outcomes.
- Unobserved pairs are not ties, and disconnected pairs cannot be asserted comparable.
- Equal exposure and full common judge panel produce sensible majority results; sparse unbalanced exposure exposes a warning.
- BT fit converges for ordinary cases, remains finite for undefeated cases with λ>0, flags disconnected components, stable under project ID permutation up to identifiability normalization.

### 14.2 Rubric properties

- Min criterion inputs yield score 0, maxima yield 100 independent of different criterion ranges.
- Scaling all weights by same positive constant does not change result.
- One additional judge cannot change the result by increasing review count alone; only their submitted scores can.
- Judge calibration must not be labeled reliable without shared-project overlap.
- Zero/one valid review produces correct unavailable/insufficient variance.

### 14.3 Rating properties

- `O[p,q]+O[q,p]=1`; identical vote distributions produce exactly 0.5.
- If every rating for A is strictly above every rating for B, superiority is 1.
- Relabeling the five categories by any strictly increasing numerical mapping does not change ordinal superiority (unlike a numeric mean).
- Empty distribution yields unscored, not zero.
- Missing ratings and the neutral middle choice are distinct.

### 14.4 Room and scheduling properties

- 0% with 12 reachable projects requires 0 visits; 25% requires 3; 100% requires 12.
- 25% with 7 reachable projects requires 2.
- Frozen denominator remains unchanged if a project moves after room entry.
- One physical visit with three forms increments epoch visit count once and each completed category count at most once.
- Judge who can reach only two projects in a 12-project room uses two-project denominator under recommended policy.
- No-local-project at 100% triggers a named override or clear wait state, never a forbidden assignment.
- Scheduler refuses duplicate active reservations under concurrent requests; expiration frees only appropriate pending coverage.
- Scarce specialist is preserved when all minimums otherwise become infeasible.
- Movement hysteresis prevents repeated room ping-pong on near-equal candidates.
- Multi-challenge projects do not displace minimum coverage in unrelated competitions.

### 14.5 Simulation evaluation protocol

Generate hidden project qualities, judge-specific severity/discrimination, ordinal threshold heterogeneity, domain expertise, track/challenge membership, room layouts, durations and dropouts. Compare randomized, least-reviewed, greedy balanced, graph-aware and hybrid schedulers with identical capacities and judge cohorts. Record: minimum coverage failure rate, worst project coverage, top-1 identification accuracy conditional on simulated truth, Spearman/Kendall rank correlation, top-3 recall, median and 95th percentile time/travel, assignments per judge, comparison components and pair imbalance, late-stage reversals, audit override frequency, and fairness under missingness. Run many independent seeds and stratify by 0/25/50/100% stay thresholds. Optimize algorithm weights only on training seeds, confirm on held-out seeds; publish no unverifiable claim that a chosen heuristic is “optimal.”

## 16. Open policy decisions to freeze before coding

These do not block the proposed baseline, but must be explicit in the versioned event config:

1. **Official RELATIVE estimator:** Copeland with strict exposure/readiness requirements vs regularized BT for sparse graphs. Both can be calculated as diagnostics; only one is official per competition.
2. **Relative ranking scope:** full strict ranking per judge (recommended), and whether a judge may revise it until judging closes (recommended, revision-controlled).
3. **Room denominator:** frozen judge-reachable projects in the current entry epoch (recommended) vs full physical room roster. Use UX copy that matches the enforced semantics.
4. **Room threshold strength:** safe soft override (recommended) vs hard with explicit admin rescue.
5. **Challenge award policy:** whether the five-level endorsements alone select the winner or produce a shortlist requiring finalist comparison. Recommend the latter if top results are close.
6. **Minimum/maximum granularity:** event defaults with per-competition overrides (recommended).
7. **Active assignments at closing:** block finalization until completed, expired or explicitly canceled with reason.
8. **Extra capacity policy:** default balanced to target; late adaptive finalist scrutiny only once minimums are safe and bias controls are active.
